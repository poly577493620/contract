# 技术说明

## 1. 目标与边界

系统以采购结果为源头依据，对采购合同做可回溯的一致性复核。MVP 的完成标准不是替代法务，而是把“输入校验—解析—证据定位—三分类—结构校验—报告导出”做成可运行、可测试的闭环。离线规则基线保证没有 API Key 时仍能演示；外部模型只在用户明确选择已配置端点时调用。

## 2. 架构

```text
PDF 输入
  → 文件/页数/加密校验
  → 逐页 300 DPI PNG 渲染与图片哈希
  → 本地 RapidOCR + bbox/置信度
  → 分栏/表格阅读顺序恢复与稳定 chunk ID
  → OCR 质量门禁、缓存与追溯
  → 多条款候选与数字/币种/条件归一化
  → 规则基线 或 统一 LLM provider
  → Pydantic Schema + quote/页码/chunk 证据回查
  → Streamlit 展示 + JSON/DOCX/PDF
```

代码采用 `src/` 布局。`parsing` 不依赖 UI；`comparison` 只消费结构化解析结果；`llm` 隔离 HTTP 协议；`reporting` 只消费经过验证的 `ReviewReport`；`evaluation` 独立实施训练/盲测边界与指标。

## 3. PDF 页面 OCR 方案

解析器先检查 `%PDF-` 签名、文件大小、加密状态和页数，再由 PyMuPDF 将每页完整渲染为 PNG。RapidOCR/ONNX Runtime 在本地 CPU 上识别文本，保留页码、bbox、置信度、行号、阅读顺序、页面图片哈希、PDF 哈希以及引擎/渲染器版本。采购结果与合同的模型输入不再读取 PDF 文本层，也不存在静默回退。

阅读顺序恢复按页面、分栏、行、横坐标和表格单元格关系处理；清洗只修复确定性的空白、换行与标点，不按语义改写。原始 OCR span 与清洗后的 chunk 保持映射，使模型 quote 可以回查到页码和坐标。

每页和整份文档计算字符数、置信度、低置信比例、碎片比例及版面提示。默认 300 DPI，只有质量失败才以 360 DPI 重试一次；仍失败则返回 `ocr_quality_failed` 并停止该样本。缓存键覆盖 PDF、页面、OCR 文本哈希以及引擎、渲染器、DPI、阈值等配置。005/006 的四份文档均在 300 DPI 一次通过。

缓存身份以 PDF 内容哈希和 OCR 配置为准，不依赖上传时的临时文件名；命中后会为本次文档角色重新生成稳定 chunk 前缀。页面 PNG 先写入唯一临时文件，再以不覆盖方式发布，清单也采用一次性原子发布。这样同一文件被 Streamlit 改名、两个解析同时运行或 Windows 预览器占用已有 PNG 时，都不会再尝试删除并覆盖缓存页面。

## 4. 条款比对与提示词

条款分类覆盖主体、项目、总价、单价、数量、服务范围、增值服务、交付、合同期限、验收、付款、税率、质保、质量、违约和保密。金额、币种、数量、百分比、日期、工作日/自然日、否定和例外条件先做确定性归一化；字段级规则只比较与当前条款相关的约束，防止把税率、违约金或其他条款数字串入付款期限。

规则基线保留同类多商品、多数量、多服务和多时限候选，并对合同候选做一次性匹配，避免一个合同条款被重复复用。找不到承接证据为 `missing`，确定性约束冲突为 `different`；只有充分确定性证据才给出高置信一致，其余暂归为低置信 `consistent` 并强制人工复核。005 的 15 日/30 日和 006 的培训/应急响应均由通用规则识别，不按样本编号硬编码。

提示词位于 `prompts/`。第三阶段三模型历史门禁使用 `2026-08-28.v5`；当前文件已升级为 `2026-08-30.v6`，增加 `items[].clause_code` 必须属于 `covered_clause_codes` 的通用集合不变量。模型用覆盖清单声明已检查条款，但 `items` 只报告明确冲突或采购承诺未承接的事项，不输出一致项，最多 12 个问题。同一条款下的多个子要求必须合并；培训、应急服务和响应时限统一归入 `value_added_service`。quote 必须逐字复制对应 OCR chunk 的连续子串。合同单方新增条款不自动算差异，运行元数据由程序补齐。

## 5. 模型调用和结构校验

`OpenAiCompatibleProvider` 通过异步 `httpx` 调用统一端点；每个端点分别配置精确模型名、API 路径、温度、JSON response format、最大输出 token、超时、重试和经过白名单校验的 thinking 参数。GLM 使用 `thinking.enabled + reasoning_effort=low`，DeepSeek 使用 `thinking.disabled`，Kimi 不发送 thinking 字段。仅对 429、5xx、超时和网络/传输异常最多重试 2 次，并尊重 `Retry-After`；4xx、JSON/证据错误和空内容不盲目重试。密钥使用 `SecretStr`，审计只保存脱敏响应元数据。

LLM 响应先保存到项目内受控目录，再由 Pydantic 以 `extra="forbid"` 严格校验。随后检查 quote 是否能在指定角色、页码和 chunk 中透明归一化回查，并检查重复项、未知条款、问题编码与覆盖清单的一致性以及采购候选覆盖；失败会保留原始输出及 `.validation.json`，调用前失败另存 `.invocation.json`，不会被正则拼成“成功报告”。provider、模型、运行 ID、调用时间、耗时、token、费用、重试和结束原因全部由运行时代码补齐。

## 6. 报告与界面

Streamlit 界面明确区分采购结果和采购合同，默认选择离线规则引擎。外部模型显示 provider、精确模型名和数据出域提示，并要求逐次确认授权。界面支持结论、风险、维度、置信度和人工复核筛选；错误时保留已完成解析阶段；审计区可查看清洗片段、警告、原始模型输出和证据校验记录。当前会话 ID 与目录可见，清理操作必须二次确认且只能删除完全匹配的 `outputs/sessions/<32 位 ID>`。

DOCX 使用标准商务简报版式、固定页边距和表格宽度；PDF 使用本地 ReportLab 与 CJK 字体，无云转换依赖。样例报告经过渲染后逐页视觉验收。

## 7. 评测设计

`build-gold` 只读取 001–020 参考答案。用户已完成候选审核，正式版本 `data/gold/verified-v1.json` 共 31 条且全部为 `human_verified=true`，其中增加了用户明确确认的 005 `contract_term/missing`；`validate-gold` 返回 `ready_for_metrics=true`。021–030 仍只生成无标签哈希清单，不能进入 Gold。

正式评测按“重复次数 → 样本 → 模型”交错顺序运行，默认每模型每样本 3 次并以多数票形成问题集。单次调用失败只写入 `runs.csv`，不会中止整批；输出 missing、different、合并问题集的 micro/macro 指标、失败率、中位耗时、P95、token、成本、原始响应、人工仲裁表和 run manifest。第三阶段只运行了 005/006 × 三模型 × 1 次门禁；第四阶段仅追加一次 DeepSeek 006 复测，累计 7 个计分调用，没有继续全量评测。

字段解析准确率不再用带/无水印相似度代替。`data/annotations/field-annotations.csv` 覆盖 8 类字段、20 个训练样本、两类文档共 320 行；只有人工确认的期望值才计算命中率，否则明确输出“待标注”。

## 8. 验证、问题与改进

第三阶段修复了 PDF 文本层字序错误、模型 thinking 参数差异、临时网络失败诊断和同条款子要求拆分问题。OCR 集成抽检确认 005 的 15 日/30 日、006 的免费培训和应急响应等关键文本均能从页面图像自然识别；Gold 已包含用户确认的 005 合同期限缺失。

限定门禁中 GLM 与 Kimi 通过两个样本；DeepSeek 在 v5 的 006 因覆盖清单遗漏而失败，随后在 v6 通用不变量提示词下完成单点复测并通过核心门禁，仍提示 `acceptance`、`warranty_period` 覆盖未声明。下一决策点是由用户确定正式评测范围与费用上限：60 次单轮横评可形成初步比较，180 次三轮横评才支持多数票稳定性分析。供应商信用代码校验、签章工作流和生产审批仍属于后续能力。

报告导出层现在按实际键名显示采购结果/合同 PDF 与 OCR 文本 SHA-256；原始模型输出位置统一转换为项目相对路径，项目外路径只保留文件名，避免在 JSON、DOCX、PDF 和评测清单中暴露本机盘符、用户名或工作区。旧结果不被改写为新运行，新版可提交样例位于 `outputs/submission-samples/`。

## 9. 最终思考题技术方案

银行合同正文不应默认发送给公网模型。只有完成数据分类分级、授权、脱敏、传输加密、供应商与跨境评估、留存策略和审计审批后，才能考虑受控外部调用；更稳妥的路径是私有化部署，但仍需评估算力、峰值并发、中文长文能力、补丁升级、模型风险和运维值守。

从流水线升级为 Agent 时，应把解析、证据检索、条款抽取、确定性校验、模型复核、规则引擎、人工审批和审计记录设计成权限明确的工具。Agent 只能编排已授权工具，不能自行扩大数据范围或绕过审批。金额阈值、日期、必含条款、权限、状态机等应由确定性规则最终执行；LLM 负责语义对应、隐含冲突和解释草稿，并始终保留证据与人工否决权。

强监管环境还需要最小权限、操作留痕、数据血缘、模型/提示词/规则版本、人工复核签章、输出不可抵赖性、内部审计、异常回滚和定期科技风险评估。本说明是工程设计讨论，不是对任何具体法律义务的结论。
